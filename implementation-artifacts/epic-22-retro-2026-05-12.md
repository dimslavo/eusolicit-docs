## What Went Well

### 1. ADR-010 Pivot Executed Cleanly — Decision Trail Preserved

The 2026-05-11 pivot from AWS-managed to single-host Docker was handled as a proper architectural decision: an ADR rewrite, a decision record (`onprem-pivot-decision-2026-05-11.md`), a sprint-change-proposal, and clean epic injection via bmad-correct-course. No in-flight story mutation. Superseded stories (pe-02, pe-03) marked `done` with explicit `SUPERSEDED` banners pointing to their replacements. AWS Terraform deleted; Helm archived (not deleted) to preserve Phase-2 HA design intent.

[PATTERN] **Architectural pivots as clean ADR rewrites + sprint-change-proposal injection, never in-flight story mutation.**
When a major architectural decision is reversed mid-sprint, the correct pattern is: (1) rewrite the ADR with the new decision + rationale, (2) author a decision record document, (3) mark superseded stories `done` with SUPERSEDED banners, (4) inject new epic via bmad-correct-course. This preserves the audit trail and prevents half-delivered code from remaining in `in-progress` limbo.
IMPACT: standards_update
SEVERITY: high

### 2. Shared `_lib.sh` Pattern — DRY Infra Scripts

All three backup/restore scripts (`postgres-backup.sh`, `redis-backup.sh`, `postgres-restore-test.sh`, `redis-restore.sh`) share a common `scripts/onprem/_lib.sh` that provides logging functions, error handling, and environment loading. This eliminates copy-paste bugs in operator automation — a category that historically causes silent backup failures (wrong credentials path, inconsistent log format).

[PATTERN] **Single shared `_lib.sh` for sibling infra scripts — DRY principle applied to operator automation.**
When multiple infra scripts in the same domain (backup, restore, monitoring) share logic (credential loading, structured logging, error exits), extract shared code to `_lib.sh` sourced by all siblings. Ensures: consistent log format for `grep`-ability, single credential-path definition, uniform exit-code semantics. All 3 backup scripts in onprem-01/02 follow this pattern.
IMPACT: standards_update
SEVERITY: medium

### 3. maxmemory-policy Fix — Critical Correctness Before Launch

Story onprem-02 changed Redis `maxmemory-policy` from `allkeys-lru` to `noeviction`. This is a **critical correctness fix**: the previous `allkeys-lru` policy would silently evict Celery task records and Redis Streams consumer-group offsets under memory pressure, causing data loss that looks like normal cache behaviour. The fix was discovered during story authoring (not via an incident), which is the correct timing.

[PATTERN] **Redis maxmemory-policy must be `noeviction` when Redis holds non-cache-only state (Celery broker, Streams consumer groups).**
`allkeys-lru` is correct for pure-cache Redis. When Redis also serves as Celery broker or event-bus (Redis Streams), `allkeys-lru` silently evicts task/event state under memory pressure without error — the eviction is logged at DEBUG level only. The correct policy is `noeviction` — Redis returns an error on new writes when memory is full, which surfaces the problem explicitly rather than silently dropping data.
IMPACT: standards_update
SEVERITY: high

### 4. Every Alert Ships with a Runbook URL — CI Gate Extended to Host Layer

The PE.06 lint gate (`scripts/check_runbook_url_coverage.py`) that was built for application-layer alerts was successfully extended to cover the 10 new host-level alerts in onprem-04 (disk, memory, container restarts, WAL archiving, Docker daemon, NTP drift). Every new alert in `host-alerts.yaml` has a `runbook_url` annotation resolving to an authored runbook.

[PATTERN] **Runbook coverage CI lint gate extends naturally from app-layer to host-layer alerts.**
The `check_runbook_url_coverage.py` gate from PE.06 is topology-agnostic — it checks `runbook_url` annotations in any Prometheus rule file under `infra/observability/`. Adding host-level alerts to a new `host-alerts.yaml` file automatically falls under the same lint gate. No changes to the gate script needed; just author the runbooks. This is the compounding gate pattern from E21 working as designed.
IMPACT: standards_update
SEVERITY: medium

### 5. Auto-Sync SEV1 Root Cause Closed Structurally (onprem-05)

The 2026-05-09 `chore: auto-sync ac2fd08` commit caused a 4-hour production outage. Story onprem-05 closes the structural gap: `deploy.yml` now triggers on `workflow_run` after CI success (not parallel with CI), auto-rollback added to smoke-test failure path, branch protection enabled on `main`, and `deploy.log` upgraded to include ISO-date headers. The root cause is closed, not just documented.

[PATTERN] **Deploy pipeline CI-gate must be a `workflow_run` trigger, not a parallel `on: push` — structural fix for auto-sync outage class.**
Running CI and deploy workflows in parallel on `push: branches: [main]` means a failing commit deploys before CI catches it. Changing `deploy.yml` to `on: workflow_run: workflows: [CI]: types: [completed]` with `if: github.event.workflow_run.conclusion == 'success'` makes the CI gate structural, not advisory. Combined with auto-rollback on smoke-test failure, this eliminates the "auto-sync ships broken code to prod" failure mode.
IMPACT: standards_update
SEVERITY: high

### 6. Ansible Chosen for infra/host/ — Idempotency and Multi-Host Ready

Story onprem-06 chose Ansible over plain shell scripts for the `infra/host/` playbooks. The decision is correctly justified: Ansible is idempotent by default (safe to re-run), the inventory abstraction supports future multi-host expansion (Phase-2 standby), and the tool is industry-standard (new operators understand it). The playbook structure (01-base-system → 02-docker → 03-nginx-and-certbot → 04-debian-user → 05-firewall → 06-eusolicit-overrides) follows a clear provisioning order with a sensible dependency sequence.

[ANTI-PATTERN] **PM sprint-change-proposal "dev passes" are code seeds, not formal story completions — stories must still execute the full bmad-dev-story → bmad-code-review cycle.**
When the PM injects a sprint-change-proposal with "LANDED IN CODE" notes, the code has been sketched/outlined but has NOT gone through the formal dev-story gate. Treating PM seed passes as story completion is a false-done anti-pattern.

[ANTI-PATTERN] **On-prem infrastructure stories have an inherently wider "code gate vs live gate" gap — story AC must distinguish what's automated from what requires operator execution.**
Stories where the acceptance criteria include "execute a drill and populate §First Drill Results" cannot be code-reviewed to `done` without the drill having been executed. For E22, this means each story's `done` state requires an operator execution session, not just code review. The story template should explicitly list AC items by category: CODE-AC (reviewable) vs LIVE-AC (requires execution). Sprint-status transitions: `review` = code-reviewable ACs satisfied; `done` = all ACs including LIVE-ACs satisfied.

### 3. Root Partition Already at 85% — Below Warning Threshold Before Drills

Story onprem-04 notes the www1 root partition (`/`) is currently at **83–85% used** (13 GB free of 86 GB). The alert threshold is 85% (warning) / 90% (critical). This means:
- The warning alert will fire **before drills even begin**
- Docker image growth from deploying the observability stack will likely push it over 85%
- The actual disk fill from onprem-01 backup writes adds to `/home` but pruning failures could spill

The mitigation — moving Docker storage root to `/home/docker/` via `daemon.json` — requires a maintenance window and is tracked as a sub-task in onprem-06. This must happen **before** deploying the observability stack (onprem-03), not after.

[ANTI-PATTERN] **Infrastructure story deployment blocked by pre-existing resource pressure must be resolved before the story begins, not tracked as a follow-up.**
When www1 `/` is at 85% and the story deploys new Docker containers (Prometheus, Grafana, Alertmanager, postgres-exporter, redis-exporter), the deployment will likely breach the 90% critical threshold and trigger an alert storm during setup. The Docker storage-root migration (daemon.json to `/home/docker/`) is a prerequisite for onprem-03, not a nice-to-have. Story entry criteria for onprem-03: confirm `/` < 75% after Docker storage-root migration.

## Key Insights and Learnings

### Insight 1: The ADR-010 Pivot Was the Right Call at the Right Time

The pivot from managed-AWS to single-host Docker is justified by three factors: (1) team size (2-3 engineers, no dedicated SRE), (2) launch timeline (single-host is operational in days; RDS Multi-AZ in weeks), (3) cost model (www1 is already running; AWS managed services add significant monthly burn before revenue). The E21 "boring-tech" pattern (managed > self-managed for small teams) still applies — but "www1 Docker" IS the managed tier for this team size and stage.

### Insight 2: E22 Stories Are Primarily Operator Playbooks, Not Developer Stories

Unlike Epics 1–21 which wrote application code, E22 stories write **operator runbooks + automation scaffolding + config templates**. The "developer" doing the work is the platform-engineering operator executing drills, not an AI agent writing Python. This distinction matters for: (a) story entry criteria (operator must have www1 access, not just a local env), (b) acceptance evidence (populated §First Drill Results section, not a CI test result), (c) definition of `done` (operator attestation, not Approve verdict).

### Insight 3: The E21 "Code Gate vs Live Gate" Pattern Is Essential for E22

E21 retro Pattern E21-P5 ("Code done vs live done gates must be explicitly documented") was the most directly applicable lesson for E22. Every E22 story is entirely in "live gate" territory — the code scaffolding was created by the PM seed pass, but the live gate (drill execution, hardware provisioning, RTO measurement) is what closes each story. Future operator-execution-heavy epics should front-load this distinction in the epic spec.

### Insight 4: Sprint-Change-Proposal Injection Creates "Zombie Code" Risk

The PM's 2026-05-11 sprint-change-proposal landed code outlines for all 6 stories in a single session. This is efficient for initializing story artifacts, but creates a risk: the injected code may have gaps, incorrect assumptions, or incomplete implementations that only surface during formal bmad-dev-story passes. The 6 stories are "started but not structured" — partial code + partial runbooks + no tests. The formal dev-story passes must treat the PM seed as a starting point, not a completed implementation.
