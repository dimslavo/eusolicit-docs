# Story 12.01: Analytics Materialized Views & Refresh Infrastructure

**Status:** ready-for-dev

**Epic:** E12: Analytics, Reporting & Admin Platform
**Story ID:** S12.01
**Points:** 4
**Type:** backend

## 1. Story

As a Platform Engineer,
I want to create and maintain PostgreSQL materialized views for all analytics domains,
so that the frontend can query pre-aggregated, performant data for dashboards without impacting the transactional database.

## 2. Acceptance Criteria

1.  [ ] Five materialized views are created in the `client` database schema: `market_intelligence_view`, `roi_tracker_view`, `team_performance_view`, `competitor_intelligence_view`, and `usage_dashboard_view`.
2.  [ ] Each view contains the necessary columns to support its corresponding dashboard as defined in the PRD and UX specifications.
3.  [ ] A Celery Beat schedule is configured in the **Notification Service** to refresh the materialized views.
4.  [ ] `market_intelligence_view`, `roi_tracker_view`, `team_performance_view`, and `competitor_intelligence_view` are refreshed **daily** at 03:00 UTC.
5.  [ ] `usage_dashboard_view` is refreshed **hourly** at the top of the hour.
6.  [ ] All view refreshes use the `REFRESH MATERIALIZED VIEW CONCURRENTLY` command to prevent read locks on the dashboards.
7.  [ ] A unique index is created on each materialized view to satisfy the `CONCURRENTLY` requirement.
8.  [ ] An Alembic migration script is created within the **Client API** service (`services/client-api/`) to create the materialized views and their unique indexes.
9.  [ ] The Alembic migration script is reversible (i.e., the `downgrade` function correctly drops the views and indexes).
10. [ ] A custom management command (`flask refresh-views` or equivalent) is added to the **Client API** service to allow for manual, on-demand refreshing of specific or all views for administrative purposes.

## 3. Dev Notes

### 3.1. Technical & Architectural Context

This story lays the foundational data layer for the entire analytics suite. The core principle is to offload complex aggregations from the live application to the database via materialized views, ensuring dashboards are fast and responsive.

-   **Database:** PostgreSQL 16. Materialized Views are a key feature to be used.
-   **Service Ownership:**
    -   The materialized views themselves are database objects. Since they are queried by the `Client API` for dashboards, the creation and migration scripts belong in the `services/client-api` service's Alembic context.
    -   The scheduled refresh tasks belong to the **Notification Service** (`services/notification/`), as per the architecture document which places scheduled background tasks (excluding data ingestion) in this service.
-   **Concurrency:** It is critical to use `REFRESH MATERIALIZED VIEW CONCURRENTLY`. This requires each materialized view to have at least one `UNIQUE` index. Choose a column or combination of columns that is naturally unique (e.g., a primary key from the source table like `opportunity_id` or `user_id` if the aggregation is 1-to-1).
-   **Idempotency:** The refresh tasks should be idempotent. Running a refresh multiple times should not cause errors.

### 3.2. View Schema Definitions

The following are starting points for the materialized view schemas. The developer must consult the source data models in `EU_Solicit_Solution_Architecture_v5.md` to finalize joins and column definitions.

#### `market_intelligence_view` (in `client` schema)

-   **Source Data:** `pipeline.opportunities`, `client.bid_outcomes`
-   **Unique Index:** `CREATE UNIQUE INDEX ON client.market_intelligence_view (period, sector, country);` (assuming period is a monthly timestamp).
-   **Columns:**
    -   `period` (e.g., `YYYY-MM-01`)
    -   `sector` (CPV category)
    -   `country`
    -   `procurement_volume` (COUNT of opportunities)
    -   `total_contract_value` (SUM of awarded bid values)
    -   `avg_contract_value` (AVG of awarded bid values)
    -   `top_contracting_authorities` (JSONB array of `{name, count}`)

#### `roi_tracker_view` (in `client` schema)

-   **Source Data:** `client.bid_preparation_logs`, `client.bid_outcomes`, `client.subscriptions`
-   **Unique Index:** `CREATE UNIQUE INDEX ON client.roi_tracker_view (company_id, period);`
-   **Columns:**
    -   `company_id`
    -   `period` (e.g., `YYYY-MM-01`)
    -   `total_investment` (SUM of `bid_preparation_logs.cost_eur`)
    -   `total_won_value` (SUM of `bid_outcomes.value` where status is 'won')
    -   `bids_won` (COUNT)
    -   `bids_submitted` (COUNT)
    -   `win_rate` (bids_won / bids_submitted)
    -   `roi_percentage` ((total_won_value - total_investment) / total_investment)

#### `team_performance_view` (in `client` schema)

-   **Source Data:** `client.users`, `client.bid_preparation_logs`, `client.bid_outcomes`
-   **Unique Index:** `CREATE UNIQUE INDEX ON client.team_performance_view (company_id, user_id);`
-   **Columns:**
    -   `company_id`
    -   `user_id`
    -   `user_name`
    -   `bids_submitted_count`
    -   `win_rate`
    -   `avg_preparation_time` (AVG of `bid_preparation_logs.hours`)
    -   `proposals_generated_count`

#### `competitor_intelligence_view` (in `client` schema)

-   **Source Data:** `client.competitor_records`, `pipeline.opportunities`
-   **Unique Index:** `CREATE UNIQUE INDEX ON client.competitor_intelligence_view (competitor_id, sector);`
-   **Columns:**
    -   `competitor_id`
    -   `competitor_name`
    -   `sector`
    -   `bid_count`
    -   `estimated_win_rate`
    -   `avg_bid_value`
    -   `bidding_patterns` (JSONB of bidding frequency over time)

#### `usage_dashboard_view` (in `client` schema)

-   **Source Data:** `shared.usage_meters` (persisted from Redis), `client.subscriptions`
-   **Unique Index:** `CREATE UNIQUE INDEX ON client.usage_dashboard_view (company_id, period);`
-   **Columns:**
    -   `company_id`
    -   `period` (current billing period)
    -   `ai_summaries_consumed`
    -   `ai_summaries_limit`
    -   `proposal_drafts_consumed`
    -   `proposal_drafts_limit`
    -   `compliance_checks_consumed`
    -   `compliance_checks_limit`

### 3.3. Project Structure & Files to Modify

-   **Client API Service (`services/client-api/`):**
    -   Create a new Alembic migration file under `services/client-api/alembic/versions/`.
        -   Implement the `upgrade()` function to `CREATE MATERIALIZED VIEW ...` for all five views.
        -   Implement the `downgrade()` function to `DROP MATERIALIZED VIEW ...`.
    -   Create a new management command file (e.g., `services/client-api/src/infrastructure/cli/refresh_views.py`) and wire it into the application's CLI runner.
-   **Notification Service (`services/notification/`):**
    -   Modify `services/notification/src/workers/beat_schedule.py` to add the new scheduled tasks.
    -   Create a new Celery task file, e.g., `services/notification/src/workers/tasks/refresh_materialized_views.py`.
        -   This task will connect to the database and execute the `REFRESH MATERIALIZED VIEW CONCURRENTLY ...` SQL command.
        -   The task should be parameterized to accept the view name to refresh.
        -   The Celery Beat schedule should call this task with the appropriate view names and schedules.
