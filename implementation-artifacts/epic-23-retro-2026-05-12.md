## What Went Well

### 1. E22→E23 Gate Dependency Correctly Structured

E23's operator stories correctly require E22's live gate as a prerequisite. `pe-04-chaos-drill-execution` gates on `onprem-03 + onprem-04 live`; `pe-06` gates on `onprem-03 email+Telegram configured`; `public-sla-soak` gates on `E22 fully live`. This cascaded dependency chain is the correct pattern — operator stories must not execute against an environment that hasn't proven its infrastructure. The E23 epic file explicitly documents these dependencies in §Cross-epic dependencies.

[PATTERN] **Operator-execution stories must gate on upstream live-state evidence, not on code-gate completion of the upstream story.**
When operator stories (drills, provisioning, soak gates) depend on infrastructure from a prior epic, the dependency must be expressed as "E22 LIVE (drills executed, services running on www1)" not "E22 done (code merged)." Sprint-status `done` on an infrastructure story means CODE GATE; LIVE GATE is separate. E23 pe-04, pe-06, and public-sla-soak all correctly gate on E22 live state. This prevents running chaos drills against unprovisioned infrastructure.
IMPACT: standards_update
SEVERITY: high

### 2. Calendar Gate for SLA Disclosure — No Numeric SLA Before Soak

The `public-sla-announcement-soak-gate` story uses a 2-week calendar gate rather than a code-reviewable AC. This is the correct pattern for confidence-building gates: trust-center disclosure goes live with "Beta — best-effort availability" language, and no numeric SLA is published until 2 weeks of live operation are observed without incidents requiring posture revision. The ADR-010 pivot ratified "best-effort" as the launch posture; the 2-week gate prevents premature SLA commitments the team can't defend.

[PATTERN] **SLA disclosure gates use calendar-based soak periods, not code-reviewable ACs — publish a conservative posture first, upgrade only after observation.**
The correct sequence for a new-launch SLA: (1) Deploy "Beta — best-effort" posture card on Trust Center; (2) Run 2-week soak with zero incidents or incidents handled within stated RTO; (3) Only then publish a numeric SLA or uptime claim. Skipping the soak period and publishing a numeric SLA at launch is an integrity risk — if an incident exceeds the stated RTO before production patterns are established, the SLA is immediately breached. `public-sla-announcement-soak-gate` demonstrates this correctly.
IMPACT: standards_update
SEVERITY: medium

### 3. Rescoping Over Cancelling (pe-06 PagerDuty → Email+Telegram)

pe-06 was originally "PagerDuty rotation provisioning" and was rescoped to "email + Telegram paging via alertmanager.yaml" after the ADR-010 pivot cancelled the AWS/PagerDuty stack. The rescoped story correctly reuses the existing alertmanager.yaml receivers rather than introducing new infrastructure. Cancelling pe-06 and creating a new story would have broken audit trails; rescoping preserved the story ID, history, and cross-references.

[PATTERN] **Rescope a story when technology changes but the operational goal survives — don't cancel and recreate.**
When an architectural pivot changes the implementation technology (PagerDuty → email+Telegram), the operational goal (verifying on-call paging) survives. Rescope the story: update the Title, §Implementation Decision, and ACs; preserve the Story ID, source reference, and acceptance history. Cancelling the story and creating a new one severs the audit trail and loses the original rationale. Reference: pe-06 rescoped 2026-05-11 per ADR-010 pivot; story history preserved in §Implementation Decision.
IMPACT: standards_update
SEVERITY: medium

### 4. Drift-Recovery Coordinator Pattern (AC1-AC3 via Sub-Stories)

The drift-recovery-story correctly delegated AC1-AC3 to sub-stories (inj-01 Dependabot, inj-02 k6 baseline, inj-03 TEA reviews) while owning AC4 (Stripe circuit-breakers) and AC5 (billing metrics) directly. This coordinator pattern was first documented in Epic 13's retrospective. AC6 (coordinator gate) ensures the coordinator cannot close until all sub-stories are done. The pattern is sound — the failure mode is in execution (AC4/AC5 partial, inj-03 blocked), not in the coordinator design.

## Key Insights and Learnings

### Insight 1: The Operational Close-Out Epic Pattern Is Valid — Execution Risk Is High

E23's design (grouping operator-execution work that doesn't fit engineering epics) is architecturally sound. The pattern of collecting calendar gates, hardware drills, and long-running carry-forwards into a close-out epic prevents scope pollution of engineering epics. The execution risk is that operator-execution stories require human action (physical drill execution, hardware provisioning, soak observation) that the orchestrator cannot automate. E23 may persist in `in-progress` longer than engineering epics because the blocking items are human-gated, not code-gated.

### Insight 2: 18-Epic TEA Debt Is a Quality Risk for Phase-2

18 epics of accumulated TEA debt means: 0 stories in Epics 8–23 have independent quality validation. The revenue-critical path (billing, subscriptions, VIES validation, usage metering) has never been independently reviewed by the TEA framework. If Phase-2 builds on an unvalidated foundation, quality defects from Epics 8–23 compound. The structural fix (TEA in bmad-dev-story) must execute before Phase-2 begins.

### Insight 3: ADR-010 Pivot Created the Right Launch Scope

The E22 retrospective correctly observed that "www1 Docker IS the managed tier for this team size and stage." E23's operational close-out work validates this: 3 of 5 stories are operator-execution drills that prove the RTO ≤ 4h / RPO ≤ 24h commitment is real. A team launching with RDS Multi-AZ and EKS would have deferred these drills indefinitely; the single-host topology makes the drills achievable.

### Insight 4: The drift-recovery-story Has Been Re-Validated 7 Times Without Completing

The drift-recovery-story Dev Agent Record notes 7 validation passes (2026-04-27/04-28/04-30/05-03/05-05/05-11 partial dev pass + [VS] gate). The story is well-specified. The failure mode is not specification quality — it's the partial dev pass pattern: each session makes incremental progress (1 call site wrapped, metrics registered) without completing all AC targets. The next formal bmad-dev-story session must treat the PM seed pass as a starting point and drive to AC4+AC5 full completion before halting.
