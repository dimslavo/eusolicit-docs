## What Went Well

### 1. 8-Epic Carry-Forward Finally Closed — k6 Baseline

The k6 performance baseline (`inj-02`) had been deferred through 8 consecutive epics (E03→E05→E06→E07→E08→E13→E20→E21). PE.01 closes it decisively:

- 7 k6 scripts authored (2 reused verbatim + 5 new)
- `load-test-results.md` documents PE.01 p50/p95/p99 measurements with sizing recommendations for PE.02–PE.04
- Nightly CI regression alarm designed (>20% degradation triggers GitHub Issue)
- **Critical discovery**: AC-2.4 Seq-Scan HALT condition — FTS at 10K rows shows 289ms Seq Scan projecting to ~28s at 1M rows. PE.01 surfaced this; PE.02 fixed it via `M_PE02_opportunities_tsv_gin_index`.

[PATTERN] **Load tests as discovery tools — not just performance gates.**
PE.01's value wasn't only the baseline numbers: it discovered an architectural gap (missing GIN index on FTS) that would have manifested as a production crisis at scale. Running load tests early, even against local datasets, surfaces plan-level issues invisible to unit and integration tests.

SEVERITY: high

### 2. Cross-Story Coordination via Reserved Placeholder IDs (PE.05 ↔ PE.06)

PE.05 authored `alerting-rules.yaml` and `kraftdata-isolation-rules.yaml` with `runbook_url` annotations pointing to placeholder paths. PE.06 fulfilled all 12 runbooks (5 reserved + 7 carry-forward/epic-defined = 12 unique with KraftData collapse). The `check_runbook_url_coverage.py` CI lint gate verifies the loop closes on every PR.

[PATTERN] **Cross-story reservation pattern for URL/ID cross-references.**
When a story produces artifacts that a downstream story will reference by URL or ID, the upstream story should commit placeholder annotations in code and the downstream story fulfills them. Combined with a CI lint gate checking referential integrity, this prevents the "placeholder that shipped to production" class of defect.
IMPACT: standards_update
SEVERITY: medium

### 3. HA-by-Default Invariant Enforced via Three CI Lint Gates

Epic 21 introduced three new CI gates that permanently enforce the HA-by-default principle:

- `check_helm_pdb_and_minreplicas.py` (PE.04): New service? PDB + minReplicas ≥ 2 or lint fails
- `test_metrics_endpoint_contract.py` (PE.05): New FastAPI service? `/metrics` endpoint or test fails
- `check_runbook_url_coverage.py` (PE.06): New alerting rule? Runbook file with 6 sections or lint fails

[PATTERN] **Gate-based invariant enforcement compounds across epics.**
Once an invariant (HA, observability, runbook coverage) is encoded as a CI gate, future stories cannot regress it. This is more reliable than documentation or code review recall. The pattern: when an epic establishes an invariant, add a lint gate in the same story that makes it impossible to violate silently.
IMPACT: standards_update
SEVERITY: high

### 4. Boring-Tech ADR-010 Compliance Throughout

Every infrastructure decision in E21 chose managed > self-managed:
- RDS Multi-AZ (not self-managed Postgres HA)
- ElastiCache Replication Group (not Redis Sentinel deployed in EKS)
- Managed Prometheus (AMP) + Grafana (AMG) (not self-deployed)
- PagerDuty SaaS (not self-hosted alerting)

For a 2-3 person engineering team, this is the correct trade-off: managed services eliminate the operational burden of maintaining HA primitives while the team focuses on product features.

[PATTERN] **ADR-010 managed-service preference scales linearly with team size constraints.**
Document the team-size assumption in every infrastructure ADR. When the team grows, the review flag is: "does the team-size assumption still hold?" RDS → self-managed Postgres is a deliberate option when the team has dedicated SRE capacity; force that decision to be explicit.
IMPACT: standards_update
SEVERITY: low

### 5. Blameless Incident Process Codified (Epic 13 Pattern Extended)

PE.06 codified the blameless incident process into three durable artifacts:
- `post-mortem-template.md`: No "who" column in the Timeline table (structurally prevents blame-finding)
- `severity-definitions.md`: SEV-1/2/3 with response-time SLAs
- `incident-response-process.md`: IC-led flow with explicit handoff points

The structural approach (template enforces blamelessness, not culture alone) is the key innovation. Epic 13's retro post-mortem pattern is now a first-class project standard.

[PATTERN] **Blameless culture requires structural enforcement, not just stated intent.**
A post-mortem template that structurally excludes a "who" column in the Timeline table produces blameless outputs regardless of facilitator skill. Complement with: (1) timeline entries always describe system state or action (not actor name), (2) "contributing factors" section instead of "root cause" (avoids single-cause fallacy), (3) "verification of fix" section to confirm the issue is resolved before close.
IMPACT: standards_update
SEVERITY: medium

## What Didn't Go Well (Challenges)

### 1. Staging Environment Unavailability — FTS Baseline Captured Locally

PE.01's FTS scenarios were captured against a local 10K-row dataset because the staging environment was unavailable (stale client-api image with `PaymentRequiredError` import error blocking rebuild). Full k6 staging runs are deferred to operator validation.

The local baseline is valid for the GIN-index gap diagnosis (the Seq Scan manifests at 10K rows with 289ms — the plan is wrong regardless of scale). But the throughput numbers (requests/s, concurrency headroom) are local-only and not production-representative.

[ANTI-PATTERN] **Non-functional stories cannot close without production-representative test environments.**
AP21-01: PE.01's D-7 deviation (staging unavailable) is acceptable because the critical discovery (Seq Scan HALT) was still captured. However, the throughput baseline (requests/s, p95 at load) is unverified at production scale. Entry criteria for any load-test story must include: "Confirm staging environment has ≥100K production-representative rows and all service images are current before story begins."
IMPACT: standards_update
SEVERITY: high

### 2. FTS Seq-Scan Not Caught During Story Planning (AC-2.4 HALT Condition)

Story 21-1 AC-2 required running FTS scenarios and documenting EXPLAIN ANALYZE output. The Seq Scan condition (289ms at 10K rows, projecting to ~28s at 1M) was discovered during Pass-7 (B10) — after multiple dev passes had already completed. This forced a cascading dependency: PE.02 had to include `M_PE02_opportunities_tsv_gin_index` as a required migration to unblock the FTS performance SLO.

The gap: story planning for PE.01 should have included a pre-story check — "Does the FTS column have a GIN index?" — before estimating FTS query-plan performance.

[ANTI-PATTERN] **DB query plan analysis is a required pre-story check for FTS stories.**
AP21-02: Any story measuring FTS performance must include a story entry-criteria item: "Run EXPLAIN ANALYZE on the FTS query with the target data volume. Verify query plan shows GIN-index Bitmap Index Scan, not Seq Scan." Seq Scan on a TSVECTOR column without a GIN index is always a performance HALT at production scale (1M+ rows). This check takes 30 seconds; not doing it cost PE.01 a revision pass and PE.02 a required migration.
IMPACT: standards_update
SEVERITY: high

### 3. TEA Reviews — 16th Consecutive Epic Without Execution

`inj-03` (TEA review backlog for E08/E09 high-risk stories) has been at `ready-for-dev` for 16 consecutive epics. Epic 20's retro committed to embedding TEA as an AC gate in the dev-story template (AP20-C3). Epic 21 did not resolve this — the commitment was broken again.

The root cause is systemic: TEA review as a separate backlog item is never prioritized over feature/infra stories. The only fix is mechanical: TEA review must be an AC in the dev-story phase itself (not a separate story), with a score gate (≥80/100) blocking the `review → done` transition.

[ANTI-PATTERN] **TEA reviews as separate backlog items are never executed; embed as dev-story AC.**
AP21-03: 16 consecutive epics without a TEA score is a process failure, not a prioritization failure. The fix must be mechanical: embed TEA execution as a required AC in the `bmad-dev-story` phase template. The dev story AC format: "TEA review executed; score documented in Dev Agent Record; score ≥ 80/100 or blocking issues enumerated and resolved." ATDD must include structural assertions catching the most common TEA failure modes (per-story, not epic-level). Remove `inj-03` from the backlog — it was the wrong implementation strategy.

### 5. Operator-Deferred Production Steps Create "Code Complete But Not Live" Gap

Epic 21 delivered all infrastructure code: Terraform for RDS Multi-AZ + ElastiCache Replication Group, Helm PDB patches, Prometheus + Grafana observability stack, PagerDuty on-call rotation, 12 runbooks. But the 99.9% SLA is not yet live because three operator-deferred steps remain:

- **D-1**: PagerDuty rotation member provisioning + escalation schedules (operator action)
- **D-2**: Live production cutovers (PE.02 RDS Multi-AZ + PE.03 ElastiCache swap + PE.04 chaos drill)
- **D-3**: 2-week soak gate before public SLA announcement

This is correct design (operator-stage actions are gated appropriately), but creates confusion about what "Epic 21 done" means.

[PATTERN] **"Code done" vs "live done" gates must be explicitly documented in epic definitions.**
For infrastructure epics with operator-deferred production steps, define two explicit gates in the epic spec: (1) CODE GATE — all Terraform, Helm, runbook, and observability code merged and CI-passing; (2) LIVE GATE — all operator production steps executed and soak period complete. Epic `done` status in sprint-status corresponds to CODE GATE only. LIVE GATE is tracked as a separate operator-managed checklist outside sprint-status. This prevents the ambiguity of "is the SLA live?" confusion after an epic closes.

## Key Insights and Learnings

### Insight 1: Platform Engineering Epics Require Dedicated Staging Environments

All six PE stories required either staging or production environments for meaningful validation. The pattern of deferring staging setup to "D-2" or "D-7" deviations means the story ships code that has never been validated against a representative environment. For future PE-class work, staging environment readiness must be an explicit story entry criterion, not a discovery during the dev pass.

### Insight 2: Multi-Story Epics with Hard Upstream Dependencies Require Explicit Dependency Tracking

PE.01 → PE.02 → PE.03/PE.04 → PE.05 → PE.06 forms a strict dependency chain. This worked because it was explicitly documented in the epic spec. The pattern of "story N consumes outputs from story N-1 as hard inputs" must be documented in the dependency graph before the first story begins. Stories that begin without knowing their upstream dependencies produce blocked dev sessions.

### Insight 3: The Two-Gate Close Pattern (AP17-C1) Is Now Embedded Culture

AP17-C1 (dev pass alone does NOT set Status: done; bmad-code-review Approve is the second gate) is now established across 9 consecutive stories (S19-0/S19-1/S19-2/S20-0/S21-1/S21-2/S21-3/S21-4/S21-5 → pending S21-6). The gate is understood and respected across all agent sessions. The remaining gap is mechanical implementation of the Status: patch as part of the Approve verdict workflow.

### Insight 4: Epic 21 Closes the PE Debt Arc — Remaining Technical Debt is Application-Layer

With PE.01–PE.06 complete (code gate), the infrastructure debt from E01–E20 is substantially resolved:
