## Part 1: Epic 16 Review

### What Went Well

**[PATTERN]** `IMPACT: standards_update` `SEVERITY: high`
**AST-level structural tests are now the standard for security property verification.** `test_static_security.py` in the integrations-api service demonstrates the pattern: (1) `test_outbound_dispatch_uses_resilience_pattern` walks the AST to confirm `@resilience_pattern` is applied to the dispatch function, (2) `test_hmac_compare_digest_not_used` confirms inbound HMAC comparison is absent (as expected for an outbound-only service), (3) `test_no_plaintext_webhook_url_logging` walks all `logger.*` call sites and asserts none pass `webhook_url=` or `decrypted_url=` as kwargs. This is the most robust form of security contract enforcement because it is immune to refactors that rename or move code. Reference: `services/integrations-api/tests/unit/test_static_security.py`.

**[PATTERN]** `IMPACT: standards_update` `SEVERITY: high`
**Shared crypto helper (`eusolicit_common.crypto.FernetCrypto`) is the canonical Fernet implementation.** The prior art lived in `notification/core/token_crypto.py`. E16 promoted Fernet encryption to `eusolicit-common` so any new service requiring at-rest encryption imports the same tested helper. The decryption happens inside the dispatch function immediately before the HTTP POST and is never stored in a variable beyond that scope. Follow-up: `notification-service` should be migrated onto the shared helper in a future story (currently tracked as Known Deviation in S16.0).

**[PATTERN]** `IMPACT: standards_update` `SEVERITY: medium`
**Consumer group naming `cg:{service}:{stream}` prevents cross-service event collision.** `integrations-api` uses `cg:integrations-api:alerts`, distinct from `notification-service`'s consumer group on the same `alerts` stream. Both services receive every event independently. This is the correct multi-consumer pattern for the EventBus architecture — document in the Redis Streams section of project-context.md for any future service that subscribes to an existing stream.

**[PATTERN]** `IMPACT: standards_update` `SEVERITY: medium`
**`--fail-on-skipped` CI gate backed by a `pytest_sessionfinish` hook.** The integrations-api CI gate uses `pytest --ignore-glob='**/integration/**' --strict-markers --fail-on-skipped`. The `--fail-on-skipped` flag is enforced by a custom `pytest_addoption` + `pytest_sessionfinish` plugin in the service `conftest.py` (not relying on the flag alone, which may not exist in older pytest versions). This ensures the gate fails hard if any test is left with `@pytest.mark.skip` or `pytest.skip()`. All new services must adopt this pattern in their `conftest.py`.

**[PATTERN]** `IMPACT: standards_update` `SEVERITY: medium`
**Idempotency constraint keyed on `(workspace_id, alert_id, webhook_id)` is the correct per-delivery granularity.** The initial implementation used `(workspace_id, alert_id, integration_type)` which silently dropped dispatches for the second active Slack webhook in the same workspace (B12). The fix: include `webhook_id` in the unique constraint so idempotency tracks per-delivery-destination, not per-workspace-type. Rule: when designing idempotency tables for fan-out consumers (one event → N deliveries), the unique key must include the delivery target identifier, not just the event identifier and a category.

### Challenges and Anti-Patterns

**[ANTI-PATTERN]** `[ACTION]` `IMPACT: config_tuning` `SEVERITY: critical`
**Skeleton delivery on first dev pass — 4 review passes to reach Approve (AP16-01).** The first dev pass produced a service that could not start: `main.py` absent, all 12 tests decorated with `@pytest.mark.skip`, CRUD handlers returning placeholder dicts, no consumer. The Zero-Output Guard (PB-ZEROOUT-007) was violated — the story moved to `review` status despite zero real implementation. The root cause is agent confidence miscalibration: the agent scaffolded the directory structure, wrote stub handlers, and treated the structural task completion as sufficient for a review handoff. Mitigation: require the pre-review checklist to include "service starts (`uvicorn` executes past startup)", "at least one real test passes (not just `--collect-only`)", and "Dev Agent Record lists actual pytest summary line (not just file count)".

**[ANTI-PATTERN]** `[ACTION]` `IMPACT: prompt_adjustment` `SEVERITY: high`
**Port collision cascaded across two remediation passes (AP16-02).** Pass 2 assigned `integrations-api` to port 8002 (conflict with admin-api). Pass 3 corrected to 8006 (still a conflict with admin-api's actual docker-compose mapping). Pass 4 (final) resolved to 8007 cleanly. Three passes to fix a one-line change because: (a) the developer did not verify the actual running port of admin-api in docker-compose before assigning the new port, (b) CLAUDE.md's port table was not consulted. Mitigation: before assigning a port to a new service, the dev agent must explicitly read `docker-compose.yml` and list all host-port mappings to find a free port. The story spec for any new service must include the target port as a named constant in the ACs.

**[ANTI-PATTERN]** `[ACTION]` `IMPACT: standards_update` `SEVERITY: high`
**Story file header not updated to `done` after final review Approve (AP16-03).** S16.0 received REVIEW: Approve in Pass 4 (`6.d` section). The sprint-status.yaml was updated to `done`, but the story file header still reads `Status: review`. This is now the 5th occurrence of this specific discrepancy (E09, E12, E13, E15, E16). The sprint-status being correct (`done`) but the story file being stale caused the NFR report to incorrectly classify the story as having an unresolved blocking finding. **Fix applied in this retrospective.** The `2b-dev-story-verify` orchestrator phase must cross-check story file `Status:` against sprint-status value before allowing the next phase to proceed.

**[ANTI-PATTERN]** `[ACTION]` `IMPACT: prompt_adjustment` `SEVERITY: high`
**Circuit-breaker outer layer absent from `eusolicit_common.resilience` (AP16-04).** The `@resilience_pattern` decorator provides retry with exponential backoff only. The consumer docstring explicitly acknowledges "the circuit-breaker layer is provided by the same helper **as it matures**". This means E16's AC-4 #6 ("circuit breaker (outer) wrapping retry") is unmet. The structural test only validates that `@resilience_pattern` is applied — it does not validate circuit-breaker semantics. This is the same Rule 47 / E04 two-layer resilience requirement that has been documented since Epic 4. Mitigation for E17: either implement a `circuit_breaker` primitive in `eusolicit-common.resilience` (preferred — shared once, used everywhere) or require explicit composition `circuit_breaker("name")(resilience_pattern(...))` and update the structural test to verify both layers.

**[ANTI-PATTERN]** `[ACTION]` `IMPACT: prompt_adjustment` `SEVERITY: high`
**Epic spec ACs vs story spec ACs gap: throttle, i18n, frontend UI all absent from story (AP16-05).** The E16 epic spec explicitly lists: (a) Redis SETNX throttle (max 1 notification per opportunity per event-type per workspace, 1h TTL), (b) BG/EN i18n locale support for notification content, (c) Slack/Teams configuration UI in workspace settings with tier-gate. Silence in the story spec means silence in implementation.

## Key Learnings for Epic 17

1. **[PATTERN] AST structural tests are the gold standard for security contract enforcement.** Any story introducing outbound HTTP calls must include: (a) test confirming resilience pattern is applied, (b) test confirming circuit-breaker is applied (when E17 implements it), (c) test confirming sensitive values (tokens, keys, URLs) are never logged as named kwargs.

2. **[PATTERN] Shared crypto helper eliminates per-service Fernet reimplementation.** E17 stores CRM OAuth tokens — use `eusolicit_common.crypto.FernetCrypto`. Do not reimplement.

3. **[ANTI-PATTERN] New service scaffolding requires a pre-review "service starts" check.** The first dev pass on any new service must verify the service actually starts (`uvicorn ... --workers 1` exits with code 0 under test settings) before the dev agent emits HALT.

4. **[ANTI-PATTERN] Epic spec → story spec coverage must be explicitly verified.** Before `create-story` for any story in a single-story epic, confirm the story ACs cover all epic-level ACs. Gaps must be named (deferred to follow-up story X) — not silently absent.

5. **[ANTI-PATTERN] k6 and OWASP are now E17 kickoff blockers, not backlog items.** After 10 consecutive carry-forwards, the orchestrator gate for E17 Story 17-0 must include: `inj-02-k6-performance-baseline: done` AND `inj-01-dependabot-configuration: done`.
